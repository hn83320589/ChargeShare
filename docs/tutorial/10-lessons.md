# 第 10 章　除錯案例與經驗

這一章收錄本專案開發過程中**真實發生**的 10 個問題。每個案例都依「症狀 → 發現方式 → 根因 → 修正 → 教訓」整理，
對應的修正都可以在 git 歷史中找到。

它們有一個共同點：**看起來是對的**。程式能跑、大部分測試通過、數字看起來合理——直到從另一個角度檢查。

---

## 案例 1：每支樁 3.7 / 3.8 kW，而不是 3.75 kW

| | |
|---|---|
| 症狀 | 8 支樁應該各 3.75 kW，實際是 3,700 / 3,800 / 3,700 / …；防振盪測試多下達了一次 |
| 發現方式 | 單元測試（驗收 3） |
| 根因 | 注水法在每一步各自向下取整到 100 W，前面捨去的零頭留在剩餘預算裡被後面的樁拿走；而且 100 W 的級距根本表達不了 3,750 |
| 修正 | 先求共同水位、**一次**捨去；級距改為 50 W |
| 教訓 | 捨入在迴圈中的**位置**很重要。另外，參數（級距）可以從驗收數字反推 |

這個 bug 同時影響兩個測試：分配不均讓防振盪測試多調整一次，因為零頭在下一次重算時落在不同的樁上。
**一個根因、兩個症狀**——修好根因，兩個測試一起轉綠。

## 案例 2：逾時關閉連線後，系統沒發現樁離線

| | |
|---|---|
| 症狀 | （潛在）心跳逾時關閉的樁，資料庫仍顯示在線，也不會保留額度 |
| 發現方式 | 寫完後自我審查 |
| 根因 | `close_stale()` 先把連線移出清單再關閉 socket。接收迴圈結束時呼叫 `unregister()`，發現連線已不在清單裡，回傳「已被取代」，於是跳過離線處理 |
| 修正 | `close_stale()` 只關閉 socket，離線處理統一由接收迴圈結束時負責 |
| 教訓 | **一件事只讓一個地方負責**。兩個地方都能「清理」同一個狀態，就會有一方以為另一方做過了 |

## 案例 3：模擬期間實際功率 30.1 kW

| | |
|---|---|
| 症狀 | 30 分鐘模擬的真實功率峰值 30,109 W，超過上限 |
| 發現方式 | 端對端測試**通過後**，額外印出詳細數據檢查 |
| 根因 | 模擬樁收到上限後隨機 2–8 秒才套用。先收到「調升到 7 kW」（延遲 8 秒）、再收到「調降到 3.5 kW」（延遲 2 秒）時，調降先生效，之後舊的 7 kW 才套用並蓋掉它 |
| 修正 | 套用時間單調遞增、以序號保護，舊設定不能蓋掉新設定 |
| 教訓 | (1) 測試通過不代表沒問題，第一次就過的測試要多看一眼數據。(2) **模擬器必須忠實於約定**：真實的樁依序套用設定，模擬器不這樣做，測的就不是同一個世界 |

值得注意的是，伺服器的分配完全正確——每個時間點下達的上限總和都 ≤ 30 kW。
問題在執行端，而只有量測**真實瞬間功率**的 `FleetMonitor` 能發現它。

## 案例 4：我寫錯的測試預期

| | |
|---|---|
| 症狀 | PowerManager 測試失敗：預期 CP01 重連後收到 3,750 W，實際收到 4,250 W；預期調降失敗時所有樁都 ≤ 3,750 W，實際有 3 支調升到 4,500 W |
| 發現方式 | 測試失敗 |
| 根因 | **測試的預期錯了**。CP01 重連後重新加入分配（7 支平分 → 4,250 W）是正確行為；調降失敗時，保守預算仍容許部分調升，總和剛好 30 kW 也是正確行為 |
| 修正 | 修正測試預期，並改成檢查真正的不變量（最壞情況總和 ≤ 30 kW） |
| 教訓 | 測試失敗時先問「**誰錯了？**」。不要反射性地改程式讓測試通過，也不要反射性地改測試。回到規格推演一次正確答案 |

## 案例 5：範例資料的最近 1 小時曲線是空的

| | |
|---|---|
| 症狀 | 儀表板的歷史曲線全是 0 |
| 發現方式 | 截圖時用眼睛看 |
| 根因 | 產生 60 天資料的迴圈是 `range(60)`，從 60 天前到**昨天**，漏了今天 |
| 修正 | 天數改為 `(今天 − 起始日) + 1`，並過濾掉晚於現在的到達時間；加回歸測試 |
| 教訓 | 差一錯誤（off-by-one）在「包含今天嗎？」這類問題上特別常見。**用眼睛看產出**也是一種測試 |

## 案例 6：公開的預設金鑰可以偽造管委會登入

| | |
|---|---|
| 症狀 | 用 repo 裡的預設字串 `"dev-only-change-me"` 簽出 `{"admin": true}` 的 cookie，直接進入管委會儀表板 |
| 發現方式 | 外部程式碼審查 |
| 根因 | 第一次被安全檢查提醒時，只做了「使用預設值時記一行 WARNING」。但 WARNING 什麼都防不了：金鑰公開，任何人都能簽 |
| 修正 | 刪除預設金鑰；未設定時首次啟動產生隨機金鑰，存檔（權限 0600）。預設管理員密碼則**拒絕啟動**，除非明確加上 `--dev` |
| 教訓 | (1) **不安全的預設值不應該存在**，讓預設狀態本身就是安全的。(2) 評估影響時要連到業務後果：偽造管委會身分 → 可以「手動釋放額度」→ 釋放仍在供電的樁 → 超過 30 kW → 跳電，正是這個系統要防止的事 |

## 案例 7：電表歸零後，交易永遠無法結束

| | |
|---|---|
| 症狀 | 樁重開機後電表從 0 開始。`StopTransaction` 回 InternalError，樁無限重送，交易停在「進行中」，度數與金額都是空的 |
| 發現方式 | 外部程式碼審查（審查者修改模擬器實驗） |
| 根因 | 把「讀數倒退」當成資料錯誤而拒絕。但 CALLERROR 不快取、樁會重試，而重試永遠得到同樣的錯誤 |
| 修正 | 讀數下降視為電表重置，分段累加計費；一律收下，標記「待管委會確認」 |
| 教訓 | **fail fast 不等於一有異常就拒絕**。對外部系統回錯誤等於要求它重試；可預期的現場狀況應該收下、記錄、交給人判斷。另外，第 2 章的 FMEA 表當初漏了「電表歸零」這一列 |

## 案例 8：CI 偶發「Future exception was never retrieved」

| | |
|---|---|
| 症狀 | GitHub Actions 上端對端測試偶發失敗，本機從未重現 |
| 發現方式 | CI（端對端測試斷言「沒有任何 ERROR log」） |
| 根因 | 送出 CALL 前先登記等待用的 Future；連線剛好在 `send()` 時中斷，連線關閉流程把 Future 設成例外，但送出端走 `send()` 的例外分支、從未讀取它 |
| 修正 | 送出端在 `finally` 移除並讀取自己的 Future。**伺服器的 `ChargerConnection.call` 也有一模一樣的問題**，一併修正 |
| 教訓 | (1) 偶發失敗是真的 bug，不要自動重跑掩蓋。(2) 「沒有 ERROR log」這種看似過度嚴格的斷言非常有價值。(3) 找到一個 bug 後，**搜尋同樣的模式**——同類的 bug 常常不只一個 |

## 案例 9：CI 上重開機發生在充電之前

| | |
|---|---|
| 症狀 | CI 偶發：重開機情境的測試 `reboots == 0` |
| 發現方式 | CI |
| 根因 | 故障排在「模擬開始後第 5 分鐘」。CI 機器較慢，120 倍速下 CP04 拖到第 6.6 分鐘才開始充電，重開機發生在充電之前 |
| 修正 | 故障時間從「開始充電」起算 |
| 教訓 | 時序相關的情境要以**事件**為錨點，不要以絕對時間為錨點。在快的機器上「剛好來得及」的假設，在慢的機器上就會破功 |

## 案例 10：啟動時範例資料產生失敗

| | |
|---|---|
| 症狀 | 在某個時間啟動伺服器時，產生範例資料失敗：`NOT NULL constraint failed` |
| 發現方式 | 實機驗證時剛好在那個時間點啟動 |
| 根因 | 啟動前 1 分鐘才開始的範例充電沒有中間讀數，批次寫入空串列時，SQLAlchemy 產生 `INSERT ... DEFAULT VALUES` |
| 修正 | 空串列時不寫入；加回歸測試（直接建構只有一筆讀數的情境） |
| 教訓 | 原本的測試固定在 21:30，所以永遠測不到。**固定的時間讓測試穩定，但也讓某些情況永遠不會出現**——邊界情況要另外刻意建構 |

## 綜合觀察：bug 是怎麼被找到的？

| 發現方式 | 案例 |
|---|---|
| 單元測試 | 1、4 |
| 自我審查 | 2 |
| 測試通過後檢視數據 | 3 |
| 用眼睛看畫面 | 5 |
| 外部程式碼審查 | 6、7 |
| CI（不同的機器與時序） | 8、9 |
| 在不同時間實際執行 | 10 |

沒有任何一種方法能抓到全部。單元測試抓不到案例 3（它需要真實的執行時序），
CI 抓不到案例 7（測試沒想到要讓電表歸零），外部審查抓不到案例 8（它只在特定時序出現）。
**驗證手段要多樣化**，而且每多一種角度，就多抓到一類問題。

### 共通的修正流程

每個案例都遵循同一個流程：

1. **重現**：寫一個確定會失敗的測試（案例 7 甚至直接用審查者給的數字）。
2. **確認 red 的原因正確**（第 9 章 9.2）。
3. **修根因**，不是修症狀。
4. **搜尋同類問題**（案例 8 因此多找到一個伺服器端的 bug）。
5. **提交訊息寫清楚「為什麼」**，讓未來的人能從 git 歷史理解這個決定。
